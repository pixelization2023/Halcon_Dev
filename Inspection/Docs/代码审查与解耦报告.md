#### P1-1 服务定位器反模式：`MVS.Core.AppContainer` ✅ **本轮已彻底移除**

`MVS.Core/AppContainer.cs` 原本是一个全局静态容器：

```csharp
public static class AppContainer
{
    public static Func<Type, object?>? Resolver { get; set; }
    public static T Resolve<T>() { ... throw new InvalidOperationException("AppContainer.Resolver 未初始化。"); }
}
```

**它只为"取 `ILogger`"而存在**，却带来两个真实问题：

1. **隐式时序契约**：要求"容器必须先于任何控件创建就绪"，否则构造函数抛异常
   —— 这正是第 13 节"启动期白屏且日志里什么都没有"的根源；
2. **依赖关系编译期不可见**：出问题只能等运行时抛异常。

**排查中还发现一个更隐蔽的问题**：`MultiCameraSystem` **从来没有给 `Serilog.Log.Logger` 赋过值**
（日志是通过容器注册的 `ILogger` 实例供应的）。于是 `HalconEngine` / `HalconView` 里那句
`AppContainer.Resolve<ILogger>() ?? Serilog.Log.Logger` 的**兜底分支实际拿到的是 Serilog 的默认静默 logger**
—— 一旦走进兜底，日志会无声消失。

**修复（分三步，每步都编译+实机验证）**：

| 步骤 | 改动 | 效果 |
| --- | --- | --- |
| 1 | `HalconView` 的 `ILogger` 取用加兜底（与 `HalconEngine` 一致） | 控件构造期不再抛异常，零风险 |
| 2 | `RegisterTypes` 里把容器 logger **提升为 `Serilog.Log.Logger`** | 全局静态 logger 与容器 logger 成同一实例，写同一份文件、同一 UI 广播；兜底分支不再静默 |
| 3 | 删除 `AppContainer.cs` 与 `AttachAppContainerResolver()`；`HalconView`/`HalconEngine` 直接用 `Serilog.Log.Logger` | **静态容器定位器彻底消失** |

**验证证据**：进「运行界面」（常驻一个 `HalconView`）后日志出现新文案
`HalconView 控件已创建` —— 说明全局 logger 生效、控件不再依赖容器。

#### P1-2 WorkBench 步骤依赖改为显式注入 ✅ **本轮已完成**

`PLCWriteStep` / `MESUploadStep` 原本在 `ExecuteAsync` 里自己走 `AppContainer.Resolve<...>`：

```csharp
var plc = MVS.Core.AppContainer.Resolve<IPLCCommunicator>();   // 旧：运行时才知道依赖缺失
```

现在改成**构造函数必需参数**，并由 `WorkBenchViewModel`（从容器注入）沿 `WorkflowBuilder` 显式传入：

```csharp
// WorkBenchViewModel
public WorkBenchViewModel(IWorkflowEngine engine, IVisionInterfaceProvider visionInterface,
    ILogger logger,
    PLCModule.Interfaces.IPLCCommunicator plcCommunicator,   // ← 容器注入
    MESModule.Interfaces.IMESConnector mesConnector)         // ← 容器注入
...
builder.WritePLC(signals, timeout, _plcCommunicator);        // ← 显式传给步骤
builder.UploadMES(timeout, _mesConnector);
```

**收益**：依赖在构造期确定，缺失会立刻抛 `ArgumentNullException`（而不是执行到那一步才静默跳过）；
步骤可在测试里替换依赖。
**验证**：实机点击「工作台」→ 日志 `导航到视图: WorkBenchView` + `进入工作台界面`，
说明容器正确解析出两个依赖并完成构造。

**剩余调用点（均可接受）**：

| 位置 | 说明 |
| --- | --- |
| `HalconEngine` / `HalconView` 的 `ResolveLogger()` | 直接用 `Serilog.Log.Logger`，无容器依赖 |
| `HalconEngine` 的 `?? ` 兜底 | 保留（句法上无害） |

#### P1-3 `MESConnector` 与 `MesApiClient` 是两套平行的 MES 抽象（**未动，待你决策**）

| | `Inspection/Services/MesApiClient.cs` | `MESModule/Services/MESConnector.cs` |
| --- | --- | --- |
| 接口 | 无（具体类） | `IMESConnector` |
| 方法数 | 14 个业务方法（长码、工序管控、实时良率、日报、样品板…） | 5 个通用方法（工单、上传、产品信息、健康检查） |

而 Shell 的导航是自定义的（`MainWindowViewModel.NavigateByNameCommand` → `ExecuteNavigateByName`，
它负责同步侧栏选中态、页面标题与权限校验）。模块直接 `RequestNavigate` 会让页面切过去、
**侧栏高亮却停在旧项上**，用户会以为"点错了"。

**做法**（与 `ICameraInventory` 同一思路：契约在内核、实现在外壳）：

| 层 | 内容 |
| --- | --- |
| 内核 `MVS.Core/INavigationRequestSink.cs` | `void RequestNavigate(string viewName)` |
| 外壳 `MainWindowViewModel` | 实现接口 → 直接复用 `ExecuteNavigateByName`（选中态 / 标题 / 权限一个都不漏） |
| 注册 `App.xaml.cs` | `RegisterSingleton<MainWindowViewModel>()` + 工厂注册 `INavigationRequestSink → Resolve<MainWindowViewModel>()`，保证与 ViewModelLocator 拿到**同一个实例** |
| `SelfTestItem.TargetView` | 每项声明目标视图名（空 = 没有对应页 → 不显示按钮） |
| `SelfTestViewModel.GoToTargetCommand` | 命令 → `_navigation.RequestNavigate(target)` |

目标页映射：相机 → `CameraManagerView`；相机绑定 / 图像索引 / 配方接口 / 检测节拍 → `InspectionConfigView`；
产品配置 / 配置版本 → `ProductView`；PLC 连接 → `PLCMonitorView`；存图 / 磁盘 / 数据库 / MES → `SystemSettingsView`。
纯环境问题（Halcon 引擎、日志目录权限、授权码）没有对应页，**不显示**按钮 —— 不制造假入口。

**实机验证证据**：
```
「去处理 →」按钮数量：11
已点击第一个「去处理 →」（对应"配方与方案接口"项）
日志：导航到视图: InspectionConfigView（角色 未登录）
截图：_screenshots\21-自检跳转-检测配置.png
```

> 截图是这次改动的关键证据：页面切到了「检测配置配方」，**同时侧栏「配置」项高亮** ——
> 证明从模块发起的导航确实同步了侧栏选中态，而这正是当初不能直接用 `RequestNavigate` 的原因。
