## 0. 先纠正三个前提（当前实现到底是什么样）

你说「检测流程、多窗口绑定、检测 PCS 还不能自定义显示多少个 Halcon 控件」——先确认当前真实状态，避免方案打偏：

| 你的判断 | 实际情况 | 证据 |
| --- | --- | --- |
| 没有多窗口绑定 | 准确。**1 个窗口，写死在 XAML 里**，没有 ItemsControl、没有窗口数概念 | `Inspection/Views/DashboardView.xaml:244` 只有一行 `<halcon:HalconView Height="380" HImage="{Binding CurrentImage}" />` |
| PCS 不能分别显示 | 准确，而且更严重：**每个 PCS 到达时把上一张图 Dispose 掉**，PCS 结果表里留着已释放的句柄 | `ViewModels/DashboardViewModel.cs:398` `CurrentImage = result.OutputImage`；`:302-304` 旧图 `DisposeLater(previous)`；而 `PcsResults` 集合里对应的 `PcsInspectionResult.OutputImage` 仍指向它 |
| 检测流程要完善 | 准确。**最要命的是：现在窗口里根本显示不出图**（见问题 P0-1） | `Services/SelfTestService.cs:149` 配 `ImageOutputPattern = "image{0}"`，但 `Services/DemoVisionProgram.cs:50` 声明的输出图标参数叫 `ResultImage`（没有 `image0`）⇒ `Services/HalconInspectionService.cs:274` 取不到 ⇒ `OutputImage` 恒为 `null` ⇒ 窗口一直黑屏 |

另外，参考项目 `DO IT!!\Halcon` **并没有多窗口写法可抄**：它全局只有一个 `ImageEdeitView`（`MachineVision,Shared/Controls/ImageEdeitView.cs:18`），
`ShapeMatchingView.xaml:83` 也只实例化一个。它值得借鉴的是**两件事**：

1. 自动适配显示：`GetImageSize` → `SetPart(0,0,h-1,w-1)` → `DispObj` → `SetFullImagePart()`（`ImageEdeitView.cs:187-198`）——当前 `HalconView` 反而是用**控件像素尺寸**去 `SetPart`，比例不对（`HalconView.cs:119`）。
2. 把框/轮廓当**叠加层**画在图上，而不是把标注烧进图里（`ImageEdeitView.cs:143-180`：`DispCross` / `DispText` / `DispObj(item.Contours)`）。

**结论：多窗口这套要自己设计，不能照搬参考项目。**

## 2. 多窗口显示设计

### 2.1 配置模型（新增，落在产品方案里）

放在 `Inspection/Models/ConfigurationModels.cs` 的 `ProductConfiguration` 下，新增一节 `DisplaySettings`：

```csharp
/// <summary>检测主监控台的多窗口显示设置</summary>
public class DisplaySettings
{
    /// <summary>是否启用多窗口（false = 沿用单窗口大图）</summary>
    public bool Enabled { get; set; } = true;

    /// <summary>窗口总个数（1~16）</summary>
    public int WindowCount { get; set; } = 4;

    /// <summary>每行窗口数（0 = 自动：WindowCount ≤ 2 → 1 列，≤6 → 2 列，否则 3 列）</summary>
    public int Columns { get; set; } = 2;

    /// <summary>窗口宽高比（宽/高），默认 4:3</summary>
    public double TileAspect { get; set; } = 4.0 / 3.0;

    /// <summary>没有结果时窗口里显示什么：Empty=黑底、OriginalImage=原始输入图</summary>
    public EmptyWindowMode EmptyMode { get; set; } = EmptyWindowMode.Empty;

    /// <summary>每个窗口的绑定</summary>
    public List<DisplayWindowSpec> Windows { get; set; } = new();
}

/// <summary>单个显示窗口的绑定规则</summary>
public class DisplayWindowSpec
{
    /// <summary>窗口序号（1 开始，与列表位置一致）</summary>
    public int Index { get; set; } = 1;

    /// <summary>窗口标题（留空则显示 "PCS {PcsIndex}"）</summary>
    public string Title { get; set; } = string.Empty;

    /// <summary>绑定方式</summary>
    public DisplayBindMode Bind { get; set; } = DisplayBindMode.ByPcs;

    /// <summary>绑定目标：
    ///   Bind=ByPcs   → PCS 序号，如 "1"（对应 PcsInspectionResult.PcsIndex）
    ///   Bind=ByKey   → 上传顺序键，如 "3"（对应 PcsKey，现场真实位置）
    ///   Bind=ByImage → 图片序号，如 "2"（该图片产出的所有 PCS 依次占位）
    ///   Bind=Follow  → 跟随最新完成的 PCS（滚动刷新）</summary>
    public string Target { get; set; } = string.Empty;

    /// <summary>显示内容：ResultImage=结果图 / OriginalImage=原始输入图 / Auto=有结果图用结果图，否则原始图</summary>
    public DisplayImageSource Source { get; set; } = DisplayImageSource.Auto;

    /// <summary>是否叠加 NG 框</summary>
    public bool ShowNgBoxes { get; set; } = true;

    /// <summary>是否叠加检测项文本（"OK"/"NG" + 序号）</summary>
    public bool ShowItemText { get; set; } = true;

    /// <summary>只显示指定判定的 PCS：Any / OkOnly / NgOnly</summary>
    public DisplayJudgmentFilter Filter { get; set; } = DisplayJudgmentFilter.Any;

    /// <summary>框线颜色（留空用主题 ErrorBrush 自动推导）</summary>
    public string BoxColor { get; set; } = string.Empty;

    /// <summary>框线宽（px，1~5）</summary>
    public int BoxLineWidth { get; set; } = 2;

    /// <summary>缩放：Fit=整幅适应（推荐）/ None=1:1 可拖动</summary>
    public DisplayScaleMode Scale { get; set; } = DisplayScaleMode.Fit;
}
```

配套枚举放 `Inspection/Models/InspectionEnums.cs`：
`DisplayBindMode{ByPcs,ByKey,ByImage,Follow}`、`DisplayImageSource{Auto,ResultImage,OriginalImage}`、
`DisplayJudgmentFilter{Any,OkOnly,NgOnly}`、`DisplayScaleMode{Fit,None}`、`EmptyWindowMode{Empty,OriginalImage}`。

**序列化**：`ProductConfiguration` 是 JSON 持久化的（`ConfigurationModels.cs:389` 注释），加字段不会破坏历史配置；
`SchemaVersion` 从 2 → 3，`ProductRepository.Load` 里对 `DisplaySettings == null` 补默认值。

### 2.2 「NG 框位置可灵活设置」怎么落地

框的来源已经现成：`PcsInspectionResult.PointSets`（每个检测项一组 `BoxRegion`，`InspectionResultModels.cs:56`，
由 `HalconInspectionService.ExtractBoxes` 从 `box{i}` 输出解析）。所以**不必把框烧进图**，按窗口叠加即可：

- 位置：`BoxRegion.Row/Column/Width/Height` 直接用于 `DispRectangle1`（Halcon 行/列坐标，天然对得上）；
- 灵活项：`ShowNgBoxes`（总开关）、`ShowItemText`（是否标 OK/NG）、`BoxColor`/`BoxLineWidth`（线型）、
  `Filter`（只看 NG，或全部）；后续可再加「第几个检测项的框」（`BoxItemIndex`，-1 = 全部）。
- 若现场希望框**烧进保存的图**（存图也带标注），再单独加一个「存图时烧框」开关，不要和显示开关混在一起。

### 2.3 窗口内图像的生命周期（**这是改造的关键，也是当前 bug 的根因**）

当前 `HalconView.DisplayImage` 把外部传入的 `HObject` 直接记进 `currentDisplayedObjects`（`HalconView.cs:214`），
`ClearWindow`/`OnUnloaded` 会 `Dispose` 它们（`HalconView.cs:261-265, 316-322`）。
⇒ 同一张图绑两个窗口会**被重复 Dispose**；而 `DashboardViewModel` 又在别处 Dispose 同一张图。

**改造原则（写进代码注释，防止后人踩）**：

1. **所有权归 PCS 结果**：`PcsInspectionResult.OutputImage` 由 `InspectionOrchestrator.ClearSheet()` 统一释放
   （现在是只 `_results.Clear()` 不 dispose，`InspectionOrchestrator.cs:591-613` —— 这是**内存泄漏**）。
2. **窗口只持有引用，不持有所有权**：`HalconView` 不再把传入图像加入自己的释放列表；
   改为「窗口要显示什么，由绑定源的引用决定」。窗口自身清屏用 `ClearWindow()` 但不动外部对象。
3. **谁 Disposes 谁知道**：`DashboardViewModel` 不再 `DisposeLater(previous)`；
   若显示的是原始输入图（`QueuedFrame.Image` 在消费循环 `finally` 里被 Dispose，`InspectionOrchestrator.cs:325`），
   则必须在 `PcsInspectionResult` 上**Clone 一份原图**留给显示（新增字段 `SourceImage`），
   由 `ClearSheet()` 一并释放。
4. **窗口重建必须释放 Halcon 句柄**：`HalconView.OnUnloaded` 现在只把 `hWindow = null`（`HalconView.cs:321`），
   没 `Dispose()`。`HWindow` 是 `IDisposable` —— 窗口数变化/换产品时反复创建 `HSmartWindowControlWPF`
   会把非托管句柄漏光。改造时**必须** `hWindow?.Dispose()`，并按「先加后减、逆序销毁」的方式调整窗口数，
   避免布局抖动与句柄泄漏。

### 2.6 边界与取舍（要你拍板的地方）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 窗口上限 | **16** | 每个 `HSmartWindowControlWPF` 都有独立非托管窗口句柄 + 显存；16 个已足够，再多应转「网格墙 + 缩略图缓存」 |
| 内存 | 显示期间**同时保留**所有 PCS 图像 | 800×600 byte 单通道约 0.5MB，一张料 20 个 PCS 约 10MB，可接受；但要在 `ClearSheet` 释放（见 2.3） |
| 结果图缺失时 | `Source=Auto` 回退到**原始输入图**（继续叠框） | 现场很多 .hdev 根本不输出结果图（当前就是这样），回退能保证窗口不空 |
| 窗口数 > 实际 PCS 数 | 多的窗口显示「等待 PCS n…」占位 | 避免误以为程序卡死 |
| 每行数量 | 支持显式指定，0 = 自动 | 大屏 / 竖屏机台需求差别大 |
| 是否要按**相机**分窗 | **第二期** | 现在 `_frameIndex` 是全局自增（`MultiCameraSystem/Services/InspectionHostService.cs:205`），多相机本来就串号，见问题 P1-4；先修索引再谈按相机分窗 |

### 7.2 输入/输出模型设计

把「步骤」从"4 个字段"升级为**带端口（Port）的节点**：

```csharp
// WorkBench/Models/StepPort.cs（新增）
public enum PortDirection { Input, Output }
public enum PortDataType  { Image, Int, Double, String, Bool, Region, Tuples }

public class StepPort
{
    public PortDirection Direction { get; set; }
    /// <summary>端口名（对应 Halcon 过程的参数名，如 "Image" / "MinGray" / "out0"）</summary>
    public string Name { get; set; } = "";
    public PortDataType DataType { get; set; } = PortDataType.String;
    /// <summary>输出端口的取值来源；输入端口的绑定表达式（如 "1.out0" / "context:LaserCode"）</summary>
    public string Value { get; set; } = "";
    /// <summary>界面用：是否在流程图上显示</summary>
    public bool ShowInGraph { get; set; } = true;
}
```

`StepItem` 增加：

```csharp
public ObservableCollection<StepPort> Inputs  { get; } = new();
public ObservableCollection<StepPort> Outputs { get; } = new();
/// <summary>步骤显示名（用于绑定表达式 {步骤名}.{端口名}）</summary>
public string Alias { get; set; } = "";
```

**绑定表达式规则**（引擎执行前解析，解析失败即校验失败并给出明确原因）：

| 写法 | 含义 |
| --- | --- |
| `{方法序号}.{端口名}` 或 `{别名}.{端口名}` | 取前面某步骤的输出 |
| `context:{键}` | 取 `IInspectionContext` 里的值（如 `context:LaserCode`、`context:Image`） |
| `literal:值` | 字面量（数字/字符串） |
| `$设置项$` | 从产品方案配置取值（例如 MES 机种、存图路径） |

**各步骤的输入/输出端（建议默认值）**

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| 采集 (Acquisition) | 相机名、曝光、增益、触发源、超时 | `Image`（HObject）、`Timestamp`、`FrameId` |
| 检测 (Inspection) | `Image`、过程名/方案文件、`InputImageParam`、算法参数（任意多个，类型化） | 每个 `out{i}` 一个端口 + `box{i}` + `image{i}`（**从已加载的过程接口自动枚举**） |
| 判定 (Decision) | 条件表达式（引用上一步端口，如 `1.out0 == "OK"`） | `Passed`（bool）、`Branch`（OK/NG） |
| PLC 写入 | 点位名、数据类型、值（可引用端口） | `Written`（bool）、`AckMs` |
| MES 上传 | 字段映射（DTO 字段 ← 端口/上下文值） | `Success`、`Message`、`ElapsedMs` |

关键点：**检测步骤的输入/输出端口应该能"一键从 Halcon 过程接口拉取"**。
项目已有这个能力：`Halcon/ProcedureInterface.cs`（`InputImageParams` / `OutputImageParams` 等），
`Inspection/ViewModels/InspectionConfigViewModel.cs:248` 已经在用它拼接口信息。
工作台复用同一套接口读取，就能把 `Image` / `MinGray` / `out0` 这类端口自动铺出来，不用手敲。

## 10. 启动加载界面：为什么"加载服务没有用到"

### 10.1 现状（"设计了但没接上"的确切位置）

| # | 事实 | 证据 |

| S-3 | 进度是**假的定时器**，与服务无关 | `LoadingUserControlViewModel.cs:54-83`：`DispatcherTimer` 每 50ms 加固定数值，文案写死"正在加载配置文件/连接数据库/初始化主界面" |
| S-4 | 真正的服务初始化在 `App.OnInitialized()` 里裸做 | `App.xaml.cs:217-245`：相机 `Initialize()`（`:226`）、`InspectionHostService`（`:229`）、主界面导航（`:236`）、日志区域（`:240`） |
| S-5 | 更关键：`AppContainer.Resolver` **在 OnInitialized 才赋值** | `App.xaml.cs:222`；而 `HalconView` 构造函数里就 `AppContainer.Resolve<ILogger>()`（`HalconView/HalconView.cs:45`），`PLCWriteStep.cs:31` / `MESUploadStep` 也用它 |

### 10.2 这不是"界面没设计好"，是**初始化顺序 + 缺少编排**的问题

`App.Initialize()`（`:110-131`）里只做了：`settings.Load()` → Hsl 授权 → 主题。
`App.OnInitialized()`（`:217-245`）里做了：`AppContainer.Resolver` 赋值 → 相机 → 检测宿主 → 导航。

两者之间**没有"显示加载界面 → 跑初始化 → 报进度 → 完成后再创建 Shell"的编排**。
`CreateShell()` 位置固定且最早，所以"先显示加载界面、再加载服务、再进主界面"这个诉求在当前结构下做不出来。

### 10.3 设计：启动流程编排

推荐做法（改动最小、不破坏 Prism 生命周期）：

```
OnStartup
  ├─ 全局异常处理 + HslLicense.Initialize()
  ├─ 显示【启动窗口】（独立 Window，纯 XAML + 一个进度条/状态文本，不用 Prism 对话框）
  │     —— 此时不创建 Shell
  ├─ 后台线程按顺序跑初始化步骤，每步回写进度：
  │     1. 配置加载 (settings.Load)              ~5%
  │     2. 主题应用 (ThemeService.Initialize)     ~15%
  │     3. 日志/日志广播                            ~25%
  │     4. 数据库连通性检测（可选，失败不阻塞）      ~40%
  │     5. PLC 授权 + 通讯对象创建                   ~50%
  │     6. 相机 SDK 初始化 + 设备枚举                ~70%
  │     7. Halcon 运行时预热（首次 CreateEngine 很慢）~85%
  │     8. 检测宿主 + 主界面导航                     ~95%
  └─ 关闭启动窗口 → base.OnStartup() 继续创建 Shell（或手动 CreateShell + Show）
```

关键改动点：

1. `AppContainer.Resolver` 的赋值**必须提到最前面**（在启动窗口创建之前，甚至放进 `RegisterTypes` 之后立即执行）。
   否则 `HalconView` 这类控件在首屏就崩。
2. `App.OnInitialized()` 里的服务初始化**搬进一个 `AppStartupService`**（可测试、可按序号报进度、可重试），
   `OnInitialized` 只负责"初始化已完成 → 导航到主界面"。
3. 启动窗口用**独立 `Window`**（不注册进 Prism 对话框系统），原因：`IDialogService` 需要一个已存在的 Shell/父窗口，
   而这里恰恰是 Shell 还没创建的时刻。
4. 每一步失败要**在启动界面上显示具体原因**并给出"重试 / 跳过（降级启动）"按钮。
   现在的行为是异常被 `HandleCrash` 吞掉、写 `crash_log.txt`、`Environment.Exit(1)`（`App.xaml.cs:182-214`）——
   现场看到的是"程序闪一下就没了"。
5. 相机 SDK 初始化失败、数据库连不上、MES 不通，都应该是**可降级**的（打红叉继续启动），
   只有 Halcon 运行时不可用才算致命。

## 13.7 第二轮：多相机图片序号串号（P1-4，已修）

### 问题

`InspectionHostService` 原来用**一个全局自增计数器**给所有相机的帧发图片序号：

```csharp
var index = Interlocked.Increment(ref _frameIndex);
```

而编排器正是靠 `QueuedFrame.ImageIndex` 去匹配配方的「图片索引」（`InspectionRecipe.ImageIndexes`）。
双相机时序号会变成：

```
相机A 第1张 -> 1     相机B 第1张 -> 2
相机A 第2张 -> 3     相机B 第2张 -> 4
```

而现场期望的是「相机A 出第 1、2 张，相机B 出第 3、4 张」这类**按位置划分**的序号。
于是配方该跑第 2 张图却跑了别的相机的图 —— 表现为"检测跑过了但结果对不上"，
**而且没有任何报错**。这是整个检测链路里最难查的一类问题。

### 改动

1. `CameraBinding` 新增 **`ImageIndexes`** 字段（逗号分隔，1 开始；留空 = 自动），
   并在 `ProductView` 的相机表里加了一列可直接编辑。
2. 新增 `CameraFrameIndexPlanner`（**独立、可单测**的类，不再把这段逻辑埋在 WPF 宿主服务里）：
   - 显式配置优先；
   - 未配置时按绑定顺序分配；**只剩一台相机需要自动规划时，分配完整区间 1..ImageTotal**
     （否则单相机只会拿到 `[1]`，一张料的第 2、3 张图永远不被采集 —— 这正是探针抓出来的第三个缺陷）；
   - 槽位不够分时退化为共用序号并告警（与旧行为一致，不会更差）。
3. `startedNewSheet`（"该开新料了"）改为**按累计帧数**判定：累计收到 `ImageTotal` 帧就上报一次。
   这个语义与相机台数、每台拍几张都无关 —— 既不会每帧都报（那会把刚收到的结果反复清掉），
   也不会永远不报（自动开新料失效）。这也是探针抓出来的：我最初按"是否刚绕回"判定，
   单相机每帧都触发 `ClearSheet()`；改成"一次性闸门"后又变成谁都不上报。
4. `QueuedFrame.CameraName` 改为**逻辑名**（相机绑定里的 `Name`），取不到才退化到序列号 ——
   日志与界面里显示序列号对现场没什么意义。

### 验证

## 13.8 第三轮：单流程超时保护（P1-2）与图像队列上限（P1-3）

### P1-2 单流程超时保护

**问题**：`HalconInspectionService.RunRecipe` 是同步执行，整个消费线程就停在那一行。
某个 Halcon 过程卡住（死循环、等外部信号、内部阻塞）时，**整线静默停摆** ——
日志里什么都没有，现场只能看到"没有新结果了"，而且 `lock (engine)` 会让后续任何尝试都一起挂死。

**改动**：
1. `InspectionRecipe` 新增 `TimeoutMs`（0 = 用默认 60 秒），并在检测配置页加了可编辑列。
   取值说明：正常检测在几十到几百毫秒，超过 60 秒几乎一定是卡死而不是"算得慢"。
2. 执行体放进独立任务，用 `Task.Wait(timeout)` 做超时等待；超时即返回明确错误，消费线程不再被拖死。
3. `lock (engine)` 换成 `Monitor.TryEnter(engine, 5s)`：连"上一次执行卡住导致锁一直不释放"
   这种情况也能报出来（错误信息明确写"上一次执行可能卡住了"），而不是无限等待。
4. 超时或异常之后把该引擎标记为**不可信**（`_poisonedEngines`），下次执行前自动重建。
   不立刻 `Dispose` 是因为超时那一刻那个任务可能仍在用这个引擎对象 —— 标记 + 下次重建既安全又能恢复。

### P1-3 图像队列上限

**问题**：`_frames` 是无界 `BlockingCollection`。相机连续采集而检测跟不上时，队列无限增长，
内存被图像吃满（一张 800×600 单通道约 0.5MB，几万帧就是几个 GB）。

**改动**：容量限制为 32 帧（`MaxQueuedFrames`）。超限时**丢最旧的帧**并接收新帧，
而不是拒收新帧。取舍理由：
1. 不能阻塞 —— 相机回调里阻塞会连累整个取流；
2. 丢最新帧更糟 —— 那张图对应的料可能已经过了工位，之后永远等不到它；
3. 生产节拍是"连续过板"，已经有积压时，最新的图才最能反映当前状态。

无论选哪种都会**明确计数 + 按秒节流告警**，并在状态里报出来，让现场知道"我们在丢图、
说明检测节拍跟不上采集节拍"，而不是让它静默变成内存泄漏。新增 `DroppedFrameCount` 供自检/诊断读取。

### 验证

临时控制台探针（引用 `Inspection` 程序集，用真实服务组装编排器，**9 项全部通过**，用完已删除）：

| 检查 | 结果 |
| --- | --- |
| 连续提交 37 帧（上限 32）时全部被接受 | ✅ |
| 正好丢弃超出的 5 帧（不是拒收新帧） | ✅ |
| 超限状态下继续提交，丢弃计数递增 5 → 6 | ✅ |
| 队列积压时 `ClearSheet()` 不抛异常 | ✅ |

## 15. 导航与权限重做：改成「全显 + 进入时校验」

### 15.1 问题（你反馈的"登录权限和不登录权限，界面导航出现了问题"）

第 13.3 节里我把权限做成了"**未登录就把受限页从侧栏藏掉**"。实测未登录时：

```
侧栏只剩 7 项：监控台 / 首页 / 日志 / 仪表盘 / PLC / MES / 外观
消失的 10 项：产品 / 检测配置 / 检测设置 / 相机 / 概览 / 测试 / 运行 / 工作台 / 自检 / 设置
```

而登录后这些项会重新出现 —— 所以现象正是"**导航随登录状态变来变去**"，
在未登录（或没意识到要登录）时看，就是"合并之后界面少了一大半、功能像丢了"。

### 15.2 根因（我自己的逻辑错误，不是合并丢文件）

`BuildNavigation()` 里只有 7 项的 `RequiredRole = 0`（`DashboardView`/`Home`/`LogViewerView`/
`ResultDashboardView`/`PLCMonitorView`/`MESStatusView`/`ThemeSettingsView`），另外 10 项是 `2`。
过滤写成：

```csharp
var visible = _allNavigation.Where(i => i.RequiredRole <= role).ToList();
```

未登录时 `role = 0`，于是只剩那 7 项 —— 打印出来就是侧栏看到的 7 项。**这是必然结果，不是构建问题。**

> 排查过程记录：我一开始怀疑是旧 build 在跑，于是对比了 exe/dll/源文件时间戳、
> 在 DLL 里搜新字段名（`IsLockedForCurrentRole`/`StatusNotice` 都在）、清掉残留进程重测 ——
> 全部排除了，才回到代码本身找到这个 `Where`。**结论是设计错了，不是环境问题。**

### 15.3 第二次修正：改成「导航不拦，未登录 = 只读」

第一版修正按"导航全显 + 点受限页弹登录"实现后，实测又发现新问题：

**登录对话框是模态阻塞的。** 点一下受限页，界面被对话框挡住、invoke 不返回 ——
从操作员视角看就是"点了没反应/卡住了"。这与现场预期冲突：

> **"不登录就是运作状态、没有权限修改"** —— 意思是页面能进、能看，只是改不了。

于是定稿为这套模型：

| 维度 | 行为 |
| --- | --- |
| 导航 | **一律可点**，任何登录状态下结构一致（17 项） |
| 未登录进入任意页 | 正常进入，**不做拦截、不弹对话框** |
| 未登录时能不能改 | **不能** —— 整页只读（按钮/输入框/可编辑表格全部禁用，文字仍可阅读） |
| 提示 | 状态栏给一条只读说明；侧栏受限页显示锁角标（表示"要登录才能改"，不是"进不去"） |

### 15.4 具体改动

| 位置 | 改动 |
| --- | --- |
| `MainWindowViewModel.ApplyRoleFilter` | 不再过滤集合，导航恒为全量；只更新每项的锁角标状态 |
| `MainWindowViewModel.ExecuteNavigateByName` | **移除访问拦截**（不再弹登录对话框）；未登录时只写一条状态栏提示，然后照常导航 |
| `NavigationItem` | 新增 `IsLockedForCurrentRole`（锁角标） |
| `MainWindow.xaml` | 侧栏图标右上角锁角标；状态栏新增只读提示胶囊（`StatusNotice` / `IsNoticeVisible`） |
| `InspectionConfigView.xaml` | **整页** `IsEnabled="{Binding CanEdit}"`（WPF 向下级联，一处覆盖全页） |
| `ProductView.xaml` | 同上 |

> 做法说明：只读闸门放在**整页**而不是逐个控件上 ——
> 一处绑定即可覆盖所有按钮/输入框/可编辑表格，且未登录时整页灰掉，操作员一眼就知道"现在只能看"。
> `SystemSettingsView` 本来就是逐组绑定（`CanEditGeneral` / `CanEditVision` / …），
> 因此操作员登录后仍能按分组编辑（通用/MES/存图可改，视觉/通讯不可改），这一层保持不变。

### 15.5 验证

**1) 编译**：`dotnet build HaiKangMVS.sln` → **0 个错误**

**2) 实际启动 + UI 自动化**：未登录状态下依次点击 16 个侧栏导航，
日志里出现的视图覆盖全部页面：

```

ProductView / InspectionConfigView / SystemSettingsView / CameraManagerView / MultiCameraView

```

- **登录对话框弹出次数 = 0**（改动前是每点一个受限页就弹一次并卡住）
- 侧栏项数：修复前 7 项 → 现在 16 项（`外观主题` 计在内，清单中的"权限"项因登录改为状态栏对话框已移除）

**3) 权限闸门探针**（临时控制台工程直接读 ViewModel 属性，绕开 UI，**22 项全部通过**，用完已删除）：

## 16. 【根因】内容区一片空白：区域从来没注册过（第 13 节引入的回归）

### 16.1 现象

侧栏 17 项、锁角标、状态栏提示全部正常，**但内容区永远空白** —— 点任何导航都没内容。
导航日志却一切正常，`crash_log` 也没有任何错误。

### 16.2 定位过程

我最初怀疑是"某个视图加载失败"，但截图显示**所有**页面都是空白（6 张截图全部约 39KB）。
于是加了一段"区域快照"诊断，立刻拿到决定性证据：

```
[区域快照 导航前]     当前没有任何已注册区域（RegionManager 里是空的）
[区域快照 首次导航后]  当前没有任何已注册区域
```

**RegionManager 里一个区域都没有。** 导航"成功"只是 Prism 把视图加进了一个从未注册的区域对象。

### 16.3 根因（用 ildasm 反汇编 Prism 确认，不是猜的）

`Prism.Wpf 9.0.537` 的 `PrismApplicationBase.Initialize()` 实际流程：

```il
IL_0073:  callvirt  CreateShell()                                    → shell
IL_007c:  call      MvvmHelpers::AutowireViewModel(shell)
IL_0082:  call      RegionManager::SetRegionManager(shell, Resolve<IRegionManager>())   ← 区域挂载
IL_0093:  call      RegionManager::UpdateRegions()                                       ← 扫描视觉树、注册区域
IL_0098:  callvirt  InitializeShell(shell)
```

而 `InitializeShell` 的实现**只有一行**：

```il
IL_0002:  call  [PresentationFramework]System.Windows.Application::set_MainWindow(shell)
```

**结论：区域挂载只对 `CreateShell()` 返回的那一个窗口做。**
第 13 节 B 批为了让启动界面先显示，把 `CreateShell()` 改成返回 `SplashWindow` ——
于是 `IL_0082` / `IL_0093` 全作用在**启动窗口**身上，主窗口的 `ContentRegion` / `LogRegion`
**从头到尾没有被注册**。这就是回归的根因，而且它完全静默。

> 我一开始还以为 `InitializeShell(主窗口)` 会把区域挂过去 —— 反汇编后才确认它只设 `Application.MainWindow`。
> **看实现比猜快得多。**

### 16.4 修复

在 `App.ShowMainWindow()` 里、主窗口 `Show()` 之后，按 Prism 原样补上那两步（都是公开 API）：

```csharp
private void AttachRegionsToShell(Window shell)
{
    var regionManager = Container.Resolve<IRegionManager>();
    Prism.Common.MvvmHelpers.AutowireViewModel(shell);
    RegionManager.SetRegionManager(shell, regionManager);
    RegionManager.UpdateRegions();
}
```

### 16.5 验证（区域快照 + 截图）

修复后同一处诊断输出变为：

```
已为主窗口挂载区域管理器并完成区域注册
[区域快照 主窗口显示并注册区域后] LogRegion: 视图 0 个       ContentRegion: 视图 0 个
[区域快照 首次导航后]             LogRegion: 视图 0 个       ContentRegion: 视图 1 个，活动 DashboardView
```

**ContentRegion 里终于有视图了。** 截图对比同样直观：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 截图体积 | 39 KB（纯空白） | 87 KB |
| 画面内容 | 只有侧栏与状态栏 | 监控台完整渲染：4 张指标卡、良率环形图、设备状态、制品信息、多窗口占位提示 |

（截图存于 `D:\黑鲸鱼工作区\_screenshots\`，`01`~`07` 是修复前、`10` 是修复后。）

### 16.6 留给以后的经验

1. **自定义 Shell 时序要付代价**：只要 `CreateShell()` 返回的不是真正的主窗口，
   就必须自己补做 Prism 对 Shell 做的所有事（目前已知：`AutowireViewModel` + 区域挂载）。
2. **"导航成功"不等于"页面显示出来了"**：`RequestNavigate` 不报错，区域可能是空的。
   已保留 `LogRegionState()` 诊断（每次启动写一行区域视图数），下次这类问题一眼可见。
3. **反汇编比猜快**：本项目已有 `ildasm.exe`（`NETFX 4.6.1 Tools`），
   遇到框架行为不明时直接反汇编，比反复试错省时间。
